# 内亚古文字字词检索

西夏文、契丹小字、古突厥语、蒙古语、回鹘文、粟特语六个板块的字词检索资料库。检索侧沿用原有的多路召回 + RRF 融合；
呈现侧按学术辞书体例重做：义项分条编号、语法标注独立成栏、每条释义可追到出处文献。

```bash
./serve.sh          # http://localhost:8765
```

---

## 这一版改了什么

### 一、契丹释义的「粘连」

原数据抓取时把 CCAMC 的 HTML 结构压平了。原页面上，一个词条是这样的：

```html
<p class="exp">×赫<code>领格</code> <small>（147）</small></p>
<p class="exp">滑哥<code>领格</code> <small>（181）</small></p>
```

三层信息：**独立义项** / **语法范畴** / **出处文献编号**。旧数据里它们变成了一个
字符串：`×赫领格滑哥领格`。

抽样 20 个字页（309 个词）实测，这次压平损失了：

| | 比例 |
|---|---|
| 义项 ≥2、被连写成一串的词 | 30% |
| 原带出处编号、被丢弃的词 | 77% |
| 带语法标签、被混入释义正文的词 | 10% |

出处编号可以对上 CCAMC 的 **214 条参考文献表**——例如（181）= 爱新觉罗·乌拉熙春
《契丹文墓誌より見た遼史》，日本松香堂，2006 年 11 月。重抓之后，每条释义都能落到
具体论著上。

`tools/scrape_khitan.py` 负责重抓并保留这三层结构。

### 二、拟音张冠李戴

CCAMC 每个契丹字有两套**互相独立**的拟音：Kane 擬音（Daniel Kane）与烏拉熙春擬音
（爱新觉罗·乌拉熙春）。旧数据只存了一个值，界面标作 `Kane / 吉田`。

对所有二者取值不同的字逐一核对：**16 / 16** 全部证明旧数据存的是**乌拉熙春**的拟音，
没有一个是 Kane 的。现已分栏并列，各自署名。

### 三、字条的「释义」是拼出来的

契丹小字的原字绝大多数是表音符号，CCAMC 上字条的「釋義」栏抽查全部为「暫無解釋」。
旧站上每个字显示的释义，实际是把**包含该字的前 5 个词**的释义用「、」连起来的
（335 个有关联词的字中，272 个精确符合这条规则）。

这一版不再这样做。字条如实显示「此字未见独立释义」，并列出该字所参与构成的词；
检索命中的若是这类字，索引里会加「词义」标记——那是词的意思，不是字的意思。

### 四、字体：16.7 MB → 0.99 MB

- `tangut_n4694_v17.ttf`（11.2 MB）**文件被截断**，比其表目录声明的长度少
  229,445 字节，`loca` / `post` / `name` / `kern` / `gasp` / `GSUB` / `GPOS`
  全部越界。任何 shaper 都无法解析。它排在 CSS 字体栈第一位，所以每位访客都要
  完整下载这 11.2 MB，然后静默回退到下一个字体。已移除。
- CSS 里写的是 `fonts/Tangut_N4694_V17.ttf`，磁盘上是全小写。macOS 不区分大小写
  所以本地正常，**部署到 Linux 服务器时三个 `@font-face` 全部 404，满屏豆腐块**。
  现在文件名统一小写。
- 余下两个字体按数据实际用到的码位做子集化并转 WOFF2：6051 个西夏码位 + 410 个
  契丹码位，零缺字。

### 五、按需加载

旧版首屏无条件加载全部语料与两套字体。现在只加载当前文字的数据：契丹视图约
0.9 MB，西夏视图约 2.2 MB（未计 gzip）。

### 六、界面

去掉开机动画、假遥测（`MEM 000/6051`、`PROC ms`、实时钟、ONLINE 呼吸点）、
`┌─ ─┐` ASCII 边框与十余个装饰动画。改为单一衬线排印、发丝分隔线、单一朱砂强调色，
并补上学术站真正需要的东西：**凡例**、**引用文献表**、**条目永久链接**、
**可直接粘进论文的条目引文**（含出处）。

释义**原文照录**，不做繁简转换；需要统一显示时用检索栏的「简体显示」开关。

唯一保留的动效：古突厥语与蒙古语的**用例中，被释词以荧光笔扫过的方式标出**。理由
是功能性的——用例只有在你找到那个词之后才有用，而在不熟悉的文字里这件事本身就很难。
标注位置取自 kaikki 的 `bold_*_offsets`（覆盖 91% / 93%），缺失时回退到词头字面匹配。
`prefers-reduced-motion` 下保留高亮、去掉动画。

⚠️ 这里有个坑：kaikki 的 offsets 是 **Python 码位下标**，而 JS 按 UTF-16 码元索引。
古突厥文在星形平面，同一段文本 Python 长 8、JS 长 15——直接把下标传进 JS 会标错位置。
所以偏移量在**构建期**就解析成 `[[片段, 是否高亮], …]`，渲染端不做任何下标运算。

## 古突厥语板块

数据来自 Wiktionary/kaikki 的 Old Turkic 转储：**472 词条 · 510 义项 · 278 条用例 · 449 条词源**。

### 为什么用 JSONL 而不用 CSV

`old_turkic/output/` 下的六个 CSV 是 `kaikki-OldTurkic.jsonl` 的拍平导出，把嵌套结构压成了字符串——**和契丹那次抓取犯的是同一个错**。最要命的是 `etymology_templates` 被压成了散文，而那恰恰是词源唯一可靠的翻译依据。所以构建脚本读 JSONL。

### 检索架构

条目主键为 **(词形, 词性)**。原有的多路 RRF 融合引擎按语种扩展，未改动打分逻辑：

| 路径 | 权重 | 说明 |
|---|---|---|
| 字形 | 2.0 | 直接匹配 U+10C00–U+10C48 码位 |
| 字面 | 1.5 | 中文释义子串与字重合 |
| 拟音 | 1.8 / 0.5 | 拉丁转写与 IPA，精确／编辑距离回退 |
| 拼音 | 1.4 | 中文释义的拼音 |
| 语义 | 1.0 | 释义共现 PPMI 向量 + 同义词词林扩展 |
| **用例** | **0.8** | **新增**：碑铭译文全文。检索「于都斤」能命中用例提到它、而释义未提的条目 |

用例路径权重最低——出现在例句中比被释义所定义是更弱的证据。

### 翻译：分三层，按数据本身支持的方式处理

| 层 | 对象 | 做法 | 覆盖 |
|---|---|---|---|
| 1 | 词源 | **生成，不翻译** | 96% |
| 2 | 受控词表 | 表查 | 100% |
| 3 | 释义 / 用例译文 | 人工翻译 | 100% / 100% |

**第一层是关键。** kaikki 把词源保存为结构化模板：

```json
{"name":"inh","args":{"1":"otk","2":"trk-pro","3":"*tür(ü)k"}}
```

于是中文由结构生成——关联词取自固定词表，语言名取自 89 个语言代码对照表，**词形一律照录**：

> 继承自 原始突厥语 \*tür(ü)k；同源词：阿塞拜疆语 türk、楚瓦什语 тӗрӗк、土耳其语 Türk、乌兹别克语 turk……

没有任何一处是改写出来的，所以不存在语义漂移，也不会把某位学者的推测译成断言。凡无模板支撑的叙述性文字一律保留英文，条目内可展开「原文 source」对照。

第三层的 916 条人工翻译存于 `tools/ot_gloss_{a,b,c,d}.py`，按英文原文精确匹配。碑铭译文的专名依汉语突厥学惯例（于都斤、黠戛斯、暾欲谷、阙特勤……）。释义中英并列显示：中文是本站译文，英文是原始记载，便于核对。

## 蒙古语板块

6623 词条 · 8520 义项 · 4836 条读音 · 2690 条词源。数据同样取自 kaikki 的 JSONL。

### 传统蒙文：只收考订写法，不作机器转写

语料 95% 是西里尔蒙古文（6305/6623）。传统蒙文（ᠮᠣᠩᠭᠣᠯ ᠪᠢᠴᠢᠭ，U+1800–U+18AF）
一栏只在原始数据记载时才出现：

- 词头本身即蒙文 —— 310 条
- `forms` 中带 `Mongolian` 标注（编者考订的写法）—— 1816 条
- **合计 2126 条（32%）**，其余 68% 显示「本条未载」，而非猜测

**为什么不用 `tugstugi/mongolian-nlp` 转剩下的 68%**：该仓库确实有
`cyrillic2bichig`（方向没错），但——

1. 未发布预训练权重，须自行用 fairseq 训练；
2. 其训练目标是 8 万行歌词经**另一个在线转换器**转出的蒙文，即模型学的是模仿
   转换器，连错误一起学；
3. 更根本的是，西里尔→传统蒙文**不是确定性映射**。传统正字法保守，保留了现代
   口语已合并的音位区别，一个西里尔词可对应多个合法蒙文写法。

机器输出是关于拼写的**推测**，与编者考订的写法混排会让整栏失去可引用性。需要
逐词转写时，凡例中给出了内蒙古大学在线工具的链接供另行核查。

### 排印

传统蒙文按其实际书写方向**竖排**（`writing-mode: vertical-lr`）。字体子集保留了
GSUB/GPOS —— 蒙文是连写文字，丢掉版式表会让每个字母都退回孤立形，那是错字。

### 检索

西里尔词头与传统蒙文写法**都可直接检索**（`ranges` 支持一个语种跨多个码位区）。
蒙古语跳过拼音路——对西里尔语料没有意义。

### 翻译

传统蒙文核心（2126 词条 / 3234 义项）的**释义与用例已全部译出**，中英并列显示。
覆盖率写在页脚，由构建脚本实时算出，不是手填的。

三层做法与古突厥语一致，但多加了一层规则渲染：

| 层 | 对象 | 做法 |
|---|---|---|
| 1 | 词源 | 由 kaikki 的结构化模板**生成**，覆盖 86% |
| 2 | 受控词表 | 词性、语法标签、语义领域、格、语言名，表查 |
| 3 | **公式化释义** | 字母定义、异体指向、屈折形指向、「X 的蒙文写法」、蒙古国各省首府等，**按模式渲染** |
| 4 | 其余释义与用例 | 人工翻译，3094 条，存于 `mn_gloss_{a…g}.py` |

第 3 层是这次新加的。kaikki 里有数百条纯样板释义，例如
`The eighteenth letter of the Mongolian alphabet, written in the Mongolian script.`
或 `causative voice in -аах (-aax) of шатах (šatax, "to burn")`。这些按模式生成既
一致又省力，把人工预算留给真正有内容的释义。

## 回鹘文板块

kaikki 的 Old Uyghur 转储：423 词条 · 613 义项 · 485 例句 · 词源中文覆盖 97%。
流程与古突厥语完全一致（结构化词源生成 + 受控词表 + 公式化释义规则 + 人工翻译）。

### 转写优先，且能自愈

423 条里有 316 条以回鹘文（U+10F70–U+10FAF）书写，而 macOS 不带这个字体，构建时
也没能取到（所有字体 CDN 都被这台机器挡住了）。直接上线就是满屏豆腐块——正是本项目
一开始要修的那个毛病。

处理办法是**转写优先 + 运行期探测**：

- `@font-face` 照常声明，指向 `fonts/olduyghur.woff2`（当前不存在）
- 启动时用 Font Loading API 问一句 `document.fonts.check()`
- 没解析出来 → 索引与字头改用拉丁转写（böz、taš、yorïmaḳ），字头下方小字标「字体缺失」
- **把 `NotoSansOldUyghur-Regular.ttf` 放进 `tools/_backup/fonts-original/` 再跑
  `tools/build_fonts.py`，回鹘文字形会自动显示出来**，不需要改任何代码

转写本来也是回鹘文研究通行的引用形式，所以这不是降级，只是换了个主次。

## 粟特语板块

这一块和其他五个不同：**它不是词典配例句，而是索引配词表**。

| 来源 | 内容 |
|---|---|
| TITUS 语料 | 21,267 行 · 125,736 词次 · 24,567 词形 · 27 种文献 |
| Wiktionary 词表 | 200 条，释义为**德语 119 / 法语 40 / 英语 39 / 俄语 2** |

词头取自语料的全部词形（按频次排序），释义只有词表覆盖得到的那些。绝大多数词形
**只有用例，没有释义**——条目里会明说，不含糊过去。

### 两套转写不通用

词表用平白拉丁（`crm`、`cxš’pt`），语料用摩尼／粟特文转写体例（`՚` 表 aleph，
`β γ δ` 表擦音）。直接对字面只能匹配上 45 条。做一层折叠（去 aleph 记号、
`β→b γ→g δ→d š→s č→c ž→z`）后升到 **138 条**，一条词表释义可挂到多个语料拼写上，
最终 605 个词形带释义。

词表中 190 个词形在语料里找不到对应拼写，作为**零频词头**补入，以免整条词表条目
不可见；这类条目会标明「未见于 TITUS 语料」。

### 用例即索引

每个词形列出它出现的行，附 `文本/章节/写本/页/行` 引证与所属传统（佛教文献 8681 行、
摩尼教 4004、基督教 3531、摩尼字体其他 3512、世俗文书 1037、古代书信 407）。每形
最多存 24 行，但**真实总数照实显示**（如「共 4258 处，示 24 处」），不假装那就是全部。

语料侧无法用 `(part,文本,章节,写本,页,行)` 把 tokens 表接回 lines 表——该键有 996 行
冲突。索引改为直接对 `text_clean` 重新切词，切词规则与 tokens 表一致。

24,567 条目若按对象存，光重复的 JSON 键名就要 1 MB，因此条目以**定长数组**存放、
重复字符串（传统、文献代号、释义记录）做**内部化**：4.7 MB → 2.4 MB。

### 关于重抓

CCAMC 是一台小服务器，请求略密就会**返回 200 但只给 62 字节空响应**——不是错误状态码，
所以不校验内容的抓取器会把空页当成功。`scrape_khitan.py` 因此：

- 每页都校验必需标记，只有验证通过才写缓存；
- 连续 8 页被拒即判定为限流，立刻中止本轮，不做无谓重试；
- 只要有任何一页没取到，就**不写出** `khitan.js`，避免产生半份数据；
- 抓完后与 `_backup/khitan.original.js` 的 2350 个词形对账。410 个字页之间理应
  提到每一个词（每个词至少含一个字），所以缺词就说明某页虽然通过了内容校验、
  但「相關詞彙」是空的——这是内容校验查不出来的一种坏页。缺词同样拒绝写出。

`rescrape.sh` 在外层反复调用它，每轮之间休息 7 分钟。页面有缓存
（`tools/.cache/`），所以每轮都从上次停下的地方接着抓。

```bash
bash tools/rescrape.sh      # 断点续抓，直到取全 410 页
```

数据有两种状态，页脚会标明当前载入的是哪一种：

- **已切分版** — `scrape_khitan.py` 产出，义项分条 + 语法标注 + 出处编号
- **未切分版** — `convert_legacy_khitan.py` 产出，义项仍连写、无出处；
  但拟音归属与字条伪释义已经改正
